==================================================
0. PRODUCT VISION
==================================================

I want a production-quality OFFLINE PF (Provident Fund) Tracker and Automation app for employees.

The first target platform is ANDROID.

The app will initially be completely offline:
- No login
- No cloud database
- No server
- No online synchronization
- No internet requirement for core functionality

However, the architecture MUST be designed so that the same business logic and data model can later support:
- Windows/Desktop
- iOS
- Optional cloud synchronization
- Online backup
- Multiple-device synchronization

Do NOT implement those future features now.

The main purpose is to let an employee configure their organization's PF rules and salary schedule once, then automatically calculate and maintain monthly PF records.

The app should function as a personal PF management and automation system, not merely as a calculator.

2. CURRENT ORGANIZATION PF POLICY
==================================================

These are the current rules for my organization.

IMPORTANT:
These values are DEFAULT company rules, NOT permanently hard-coded rules.

The user must be able to change them from PF Rules/Organization Settings.

CURRENT DEFAULTS:

- PF becomes applicable after the employee completes probation and becomes permanent.
- PF start date is the Permanent Employee/PF Start Date.
- Basic Salary = 60% of Gross Salary.
- Employee PF contribution = 10% of Basic Salary.
- Employer/Company PF contribution = 10% of Basic Salary.
- Employee and employer contributions are therefore equal under the current default policy.
- PF maturity period = 2 years from Joining Date.
- Exit before maturity: employee receives own contribution; employer contribution is not received.
- Exit on maturity date: treated as MATURE.
- Exit after maturity: employee receives own contribution + employer contribution.
- PF investment/profit exists, but exact profit formula and entitlement rules are currently UNKNOWN.
- Profit must therefore be optional/manual for now.
- PF annual statement year = July 1 to June 30.
- PF statement-year configuration must be changeable for other organizations.

2 years.

- Exit Date > Maturity Date = Mature

==================================================
8. MONTHLY PF CALCULATION
==================================================

For each applicable salary/work month:

Basic Salary = Gross Salary × Basic Salary %

Employee PF = Basic Salary × Employee PF %

Employer PF = Basic Salary × Employer PF %

Total Monthly PF = Employee PF + Employer PF

Example:
Gross = 30,000
Basic % = 60%
Employee PF = 10%
Employer PF = 10%

Basic = 18,000
Employee PF = 1,800
Employer PF = 1,800
Total = 3,600

PF contribution starts only from PF Start Date.

Do not generate PF records before PF eligibility begins.

==================================================
9. SALARY MONTH VS SALARY PAYMENT DATE
==================================================

THIS IS VERY IMPORTANT.

The salary/work month and salary payment/credit date are TWO DIFFERENT concepts.

Example for my current organization:

January 2026 salary:
- Salary/work month = January 2026
- Salary is credited around February 1–5, 2026
- PF for January is calculated based on January salary
- Salary credited date belongs to February

Therefore each monthly PF record must distinguish:

1. PF/Salary Month
2. Salary Credited Date
3. Gross Salary
4. Basic Salary
5. Employee PF
6. Employer PF
7. Total PF

DO NOT move January PF into February just because January salary was paid in February.

The PF record remains:
PF Month = January 2026
Salary Credited Date = February 3, 2026, for example

13. AUTO PF CALCULATION — ON
==================================================

When Auto Calculate PF = ON and a PF scheduled generation date has arrived:

1. Check whether the PF record already exists.
2. Check whether the employee was PF-eligible for that month.
3. Identify the applicable salary.
4. Calculate Basic Salary.
5. Calculate Employee PF.
6. Calculate Employer PF.
7. Calculate Total PF.
8. Create the monthly PF record.
9. Mark it "Automatically Calculated".
10. Add it to the calculated PF balance.
11. Keep the record editable.
12. Prevent duplicate records.

If salary information is unavailable:
- Do not calculate using zero.
- Do not invent a salary.
- Mark it "Pending Salary Information".
- Show the user that action is required.

58. HISTORICAL PF RECONSTRUCTION FROM EMPLOYMENT & SALARY HISTORY
====================================================================

IMPORTANT:
The user may start using the app long after joining the company.

The app MUST NOT require the user to manually enter an opening PF balance just because the app was installed/started later.

Instead, the app must reconstruct historical PF contributions from:
- Employment information
- PF eligibility/start date
- Effective-dated PF rules
- Salary history
- Organization salary schedule

The app's App Start/Tracking Date must NOT determine when PF calculation begins.

PF calculation history should begin from the actual PF eligibility date.

REQUIRED HISTORICAL INPUTS:
1. Joining Date
2. Joining Gross Salary
3. Probation Period
4. Permanent Employee Date
5. PF Start Date
6. Salary History / Salary Changes
7. PF Rules
8. Organization Salary Schedule

The user may start using the app at any point during employment.

JOINING SALARY:
The Joining Gross Salary is the first salary-history record.
Example:
Joining Date: 01 January 2024
Joining Gross Salary: ৳30,000
Salary History automatically starts with:
Effective From: 01 January 2024
Gross Salary: ৳30,000

PROBATION:
Allow a configurable probation period.
Example:
Joining Date: 01 January 2024
Probation: 6 months
Expected Permanent Date: 01 July 2024

Because permanent status may depend on performance, the user must be able to enter/override the actual Permanent Employee Date.

PF START DATE:
PF Start Date is a separate field.
Default suggestion may be Permanent Employee Date, but the user must be able to edit it.
Do NOT assume PF always starts on Joining Date.

HISTORICAL SALARY CHANGES:
Do NOT require every month's salary manually.
Use effective-dated salary history.

Example:
01 January 2024 → ৳30,000
01 January 2025 → ৳35,000
01 January 2026 → ৳40,000

Apply:
Jan-Dec 2024 → ৳30,000
Jan-Dec 2025 → ৳35,000
Jan 2026 onward → ৳40,000

If salary changes mid-month, support a configurable policy. Do not silently invent a rule.

HISTORICAL PF RECONSTRUCTION:
When initial setup is completed, calculate all historical PF periods from PF Start Date through the latest eligible PF month using:
- Applicable PF rule for that period
- Applicable salary for that period
- Salary schedule
- Employee PF rate
- Employer PF rate
- Basic salary percentage

Generate monthly historical records with:
- PF/Salary Month
- Gross Salary
- Basic Salary
- Employee PF
- Employer PF
- Total PF
- Applicable PF rule reference
- Historical/calculated status

Mark them "Historical / Automatically Calculated".

APP START DATE VS PF HISTORY:
Example:
Joining Date: January 2024
PF Start Date: July 2024
User starts app: August 2026

Calculate historical PF from July 2024 through the latest eligible month, even though the app was not installed during those months.

CURRENT PF BALANCE:
Current Calculated PF Balance =
Historical Employee Contributions
+ Historical Employer Contributions
+ Known Profit
+ Adjustments
+ Future/current contributions as they are generated.

Do not add an artificial Opening Balance if historical monthly records have been generated.

HISTORICAL PROFIT:
Profit is optional because the exact company profit formula is unknown.
Do not estimate, invent, or treat missing profit as zero.
Display "Historical profit not entered".
Allow later entry from company PF statements.

COMPANY PF STATEMENT RECONCILIATION:
Allow comparison between calculated historical balance and official company PF statement.
Example:
App calculated: ৳125,000
Company statement: ৳128,500
Difference: ৳3,500

Do not automatically change calculated records to match the statement.

RECALCULATE HISTORICAL PF:
Provide "Recalculate Historical PF".
Warn that this recalculates calculated records using configured rules and salary history.
Official actual statement records must not be changed.
Require confirmation.

HISTORICAL RECORD EDITING:
Historical calculated records remain editable.
If manually changed, mark "Manually Adjusted" and preserve original calculated values where practical.

AUTO CALCULATE:
Auto Calculate PF ON/OFF controls future scheduled PF generation.
Historical reconstruction is a separate explicit setup action.
Auto Calculate OFF must not prevent initial historical reconstruction.

FIRST-TIME SETUP:
1. Employment information:
   - Joining Date
   - Joining Gross Salary
   - Probation Period
   - Permanent Employee Date
   - PF Start Date
2. PF Rules
3. Salary Schedule
4. Salary History
5. Historical PF Preview
6. User confirms "Generate Historical PF Records"
7. Historical monthly records are created
8. Configure persistent Auto Calculate PF ON/OFF
9. Optionally enter actual company PF statements

HISTORICAL PF PREVIEW:
Show:
PF Start
Calculation Through
Number of Months
Employee Contribution
Employer Contribution
Known Profit
Calculated PF

Allow user to review salary changes before confirming.

IMPORTANT DATA INTEGRITY:
Historical calculated PF records and actual company statement values must remain separate.
Never overwrite official actual values.
Never double-count historical records with a manual opening balance for the same period.

59. EFFECTIVE-DATED PF RULES / PF POLICY HISTORY
==================================================

PF rules can change over time.
Therefore PF Rules MUST be stored as effective-dated versions/history.

Each PF rule set must include at minimum:
- Rule ID
- Effective From Date
- Optional Effective To Date
- Basic Salary %
- Employee PF %
- Employer PF %
- Maturity Period
- Maturity Basis
- Employer Contribution Entitlement Rule
- Other applicable PF policy settings
- Notes

RULE EFFECTIVE DATE:
Every rule set has an Effective From date.

Example:
Version 1:
Effective From 01 July 2024
Basic 60%
Employee PF 10%
Employer PF 10%

Version 2:
Effective From 01 July 2025
Basic 60%
Employee PF 12%
Employer PF 12%

Use the rule version applicable to each PF/salary month.

HISTORICAL CALCULATION:
For each PF month:
1. Identify PF/Salary Month.
2. Find applicable PF rule version.
3. Find applicable salary history version.
4. Calculate using THAT period's rule and salary.

Example:
June 2025 → Version 1 → 10%/10%
July 2025 → Version 2 → 12%/12%

The July rule MUST NOT affect June or earlier calculations.

HISTORICAL IMMUTABILITY:
Adding/changing a new PF rule must NOT automatically modify previously calculated PF records.

Example:
June 2025 remains 10%/10% even after a new 12%/12% rule becomes effective July 2025.

CURRENT RULE:
Use the latest rule whose Effective From Date is on or before the PF/Salary Month.

Example:
01 July 2024 → Version 1
01 July 2025 → Version 2
01 January 2026 → Version 3

June 2025 → Version 1
July 2025 → Version 2
December 2025 → Version 2
January 2026 → Version 3

RULE END DATE:
The system may automatically derive Effective To Date from the next rule's Effective From Date.
Do not require manual end dates unless needed.

PF RULE HISTORY SCREEN:
Show:
- Effective From
- Effective To
- Basic Salary %
- Employee PF %
- Employer PF %
- Maturity policy
- Other policy values
- Current/Historical status

Allow:
- Add new rule version
- Edit future/unapplied rule
- View historical rule
- Duplicate an existing rule as a new version

PROTECT HISTORICAL RULES:
Once a rule has been used for historical calculations, prefer creating a new rule version instead of destructive editing.

If user tries to edit a historical used rule, warn:
"This PF rule has been used for historical calculations. Changing it may affect historical calculations. Do you want to create a new rule version instead?"

RULE VERSION REFERENCE:
Each monthly PF record must store the PF rule version used for its calculation.
Example:
July 2025 PF → Rule Version = PF-2025-07

This provides an audit trail.

RECALCULATION:
Historical PF records must NOT automatically recalculate when a new rule is added.
Provide an explicit "Recalculate Historical PF" action.
Show affected periods and rule versions before confirmation.
Do not modify official Actual Company Statement records.

MATURITY RULE CHANGES:
Maturity-related rules may also change and may need effective-dated versions.

Example:
Before July 2025 → Maturity 2 years
From July 2025 → Maturity 3 years

Do NOT blindly recalculate an employee's maturity date using the newest rule.
Determine which rule applies based on the organization's policy and relevant employee eligibility date.
If ambiguous, do not invent the policy; make the basis configurable and ask the user when necessary.

IMPORTANT RULE PRIORITY:
For every PF month:
PF Month
↓
Applicable PF Rule Version
↓
Applicable Salary History Version
↓
PF Calculation
↓
Monthly PF Record

CORE PRINCIPLE:
SALARY CHANGES and PF RULE CHANGES are both EFFECTIVE-DATED.

Historical Salary
+
Historical PF Rule
+
PF Eligibility Date
+
Salary Schedule
=
Historical PF Calculation

The app must never use today's salary or today's PF rule to incorrectly recalculate an old PF month.
